## Chapter 10: Autoscaling, Rollouts, and LLM MLOps Lifecycle Monitoring — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | Canary rollout vs blue-green deployment — when to use each for LLM version updates? | Canary: gradual traffic shift (e.g., 5%→25%→50%→100%) with both versions live — use when new version is state-compatible with old. Blue-green: atomic cutover between two fully separate environments — use when versions are incompatible (e.g., tokenizer/cache changes) or instant rollback is required. Exam tip: incompatibility = blue-green; gradual risk validation = canary. |
| 2 | Why is GPU utilization alone a poor autoscaling trigger for LLM serving? | Variable token generation lengths and batching can cause queue backlog and latency SLO breaches even while GPU utilization looks moderate. Better signal: combine queue depth + latency percentile breach with GPU utilization. |
| 3 | Best load balancing strategy for LLM replicas with variable response duration? | Least-connections / least-outstanding-requests routing — sends new requests to the replica with fewest active requests, avoiding overload from long-running generations. Round-robin is load-blind and performs worse here. |
| 4 | Which latency metric should NEVER be used alone to judge LLM SLO compliance? | Average latency — it masks tail latency. Always track p50/p95/p99 percentiles; p99 breaches are what users on the worst end of the distribution actually experience. |
| 5 | Define data drift vs model (concept) drift. | Data drift = shift in input distribution over time. Model/concept drift = shift in the input-output relationship (what counts as a 'correct' response changes) even if input distribution is stable. Exam distinguishes the two by what changed: inputs vs the mapping. |
| 6 | What two signal types typically combine to justify a retraining trigger? | 1) Statistical drift signal (e.g., rising embedding distance from training distribution) and 2) Quality/feedback signal (e.g., sustained rise in negative user feedback or falling eval scores). Both should be validated against a labeled eval set before committing to retraining. |
| 7 | Best capacity-planning metric for LLM endpoints serving variable-length generations? | Tokens generated per second per replica, benchmarked against throughput SLOs — not raw request count, since request count ignores variable generation length. |
| 8 | Standard canary traffic progression pattern. | Small initial exposure (commonly ~5-10%) → monitor error rate/latency/quality against thresholds → progressively increase (e.g., 25% → 50% → 100%) only if metrics stay within bounds at each stage. Rollback immediately on threshold breach. |
| 9 | What does a rising p99 latency (while p50 stays flat) usually indicate? | A tail-latency problem affecting a subset of requests — often caused by queueing/backpressure, long-generation outliers, or resource contention on a subset of replicas. Investigate queue depth and per-replica load, not just average metrics. |
| 10 | Why can canary rollout be risky for a tokenizer-incompatible LLM version update? | Canary runs both versions concurrently against potentially shared caches/state. If the new tokenizer/version is incompatible with cached artifacts from the old version, concurrent operation can produce corrupted or inconsistent outputs — blue-green's atomic cutover avoids this. |
| 11 | What monitoring signal complements error rate and latency for LLM-specific serving health? | Token throughput (tokens/sec) — captures generation speed and GPU efficiency, which generic error-rate/latency metrics (borrowed from traditional web services) don't fully reflect for LLM workloads. |
| 12 | What should happen before committing to full retraining after detecting drift signals? | Validate the drift signal's root cause against a labeled/held-out evaluation set. Drift signals alone can produce false positives; validation confirms whether retraining, fine-tuning, or no action is the right response. |
