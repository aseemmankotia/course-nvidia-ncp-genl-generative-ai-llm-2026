## Chapter 6: Customization Strategies: LoRA/QLoRA, RLHF vs DPO, and NVIDIA NeMo — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | LoRA vs Full fine-tuning: which updates all model parameters? | Full fine-tuning updates every weight; LoRA freezes base weights and trains only injected low-rank matrices (rank r, typically 4-64). Exam tip: full fine-tuning needs the most GPU memory/compute; LoRA is the default PEFT baseline. |
| 2 | QLoRA's key innovation? | Quantizes frozen base weights to 4-bit NF4 (with double quantization) and trains LoRA adapters in higher precision on top, using paged optimizers to avoid memory spikes. Exam tip: enables fine-tuning 65B-70B models on a single 80GB GPU. |
| 3 | P-tuning technique? | Prepends trainable virtual token embeddings to the input while the base model stays fully frozen. Exam tip: fewer trainable params than LoRA; good for small datasets/simple tasks. |
| 4 | Bottleneck adapters? | Small feed-forward bottleneck layers inserted between/inside transformer blocks; base weights frozen, only adapter layers trained. Exam tip: distinct from LoRA (which modifies weights via low-rank updates, not inserted layers). |
| 5 | Continued pretraining vs PEFT fine-tuning — when to use each? | Continued pretraining: adapt vocabulary/style using a large unlabeled domain corpus with the causal LM objective. PEFT fine-tuning: adapt to a specific task using a smaller labeled dataset. Exam tip: continued pretraining usually precedes instruction/PEFT tuning for large domain shifts. |
| 6 | RLHF pipeline stages? | 1) SFT base model, 2) train reward model on human preference pairs, 3) optimize policy against reward model via RL (typically PPO). Exam tip: most complex/compute-heavy alignment approach, with reward-hacking risk. |
| 7 | DPO's advantage over RLHF? | Directly optimizes the policy on preference pairs via a closed-form loss derived from the Bradley-Terry preference model — no separate reward model, no RL loop. Exam tip: simpler, more stable, fewer hyperparameters than RLHF/PPO. |
| 8 | NVIDIA NeMo Aligner purpose? | Library for preference alignment training: RLHF (reward model + PPO), DPO, SteerLM. Exam tip: distinct from NeMo Framework's PEFT/SFT recipes and from NeMo Curator (data curation). |
| 9 | NeMo Framework PEFT recipes supported? | LoRA, P-Tuning, Adapters, IA3 — selected via the model.peft.peft_scheme YAML config key. Exam tip: NeMo Framework also supports full SFT and continued pretraining recipes. |
| 10 | Data budget rule of thumb for choosing customization technique? | Small dataset (hundreds–few thousand examples) → PEFT (LoRA/P-tuning/adapters). Large dataset + large domain shift + high compute budget → full fine-tuning or continued pretraining. Exam tip: scenario questions test matching data volume/compute to technique. |
| 11 | Memory trade-off: LoRA vs QLoRA for a 70B model? | LoRA trains atop full-precision (fp16/bf16) base weights — ~140GB just for weights. QLoRA quantizes base weights to 4-bit (~35GB) plus small LoRA adapters, fitting on a single 80GB GPU. Exam tip: QLoRA trades slight accuracy/speed for large memory savings. |
| 12 | PPO vs closed-form loss — which alignment method uses which? | RLHF uses PPO, an RL algorithm requiring a reward model and rollout sampling. DPO uses a closed-form classification-style loss directly on preference pairs, no RL/rollouts needed. Exam tip: DPO removes the RL loop entirely. |
