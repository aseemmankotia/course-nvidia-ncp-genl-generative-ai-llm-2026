## Chapter 2: Scaling Laws, Tokenization, and Context-Window Mechanics — Flashcards

| # | Front (Question) | Back (Answer) |
|---|-----------------|---------------|
| 1 | Chinchilla compute-optimal ratio of training tokens to parameters? | ~20 tokens per parameter (Hoffmann et al., 2022). Exam tip: models trained on far more tokens than this (e.g., LLaMA-family) are 'inference-optimized,' not compute-optimal. |
| 2 | Default RoPE base frequency (theta) in the original rotary embedding formulation? | 10000. Context-extension techniques often increase this (e.g., to 500000+) to slow frequency decay and extend usable context. Exam tip: raising theta extends context; lowering it does not. |
| 3 | Mixtral 8x7B: total parameters vs active parameters per token? | ~47B total parameters, ~13B active per token (2 of 8 experts routed per token). Exam tip: MoE delivers large-model capacity at small-model inference compute. |
| 4 | When should you pick MoE over a dense model of similar inference cost? | When you need higher total capacity/quality across diverse tasks but must keep per-token inference cost/latency low. Trade-off: MoE requires more total VRAM to hold all experts and adds routing complexity. |
| 5 | What does Position Interpolation (PI) do to extend context length, and what does it require? | Linearly rescales (compresses) position indices to fit within the model's originally trained range. Requires additional fine-tuning to recover quality — it is NOT training-free. |
| 6 | How does NTK-aware RoPE scaling differ from plain Position Interpolation? | It scales rotation frequencies non-uniformly (less compression on high frequencies, more on low frequencies), enabling reasonable context extension often with little or no fine-tuning ('training-free'/'dynamic NTK'). |
| 7 | How does vocabulary size affect embedding table parameter count? | Embedding table params ≈ vocab_size × hidden_dim (plus a tied output/softmax layer in many designs). Doubling vocab size roughly doubles embedding table size. Exam tip: larger vocab shortens token sequences but grows model size. |
| 8 | BPE vs SentencePiece — key architectural difference? | BPE (as in GPT-2) typically assumes whitespace pre-tokenization. SentencePiece treats raw text (including whitespace) as a byte/character stream, requiring no pre-tokenization — better for CJK and multilingual text. |
| 9 | Risk of a very large vocabulary (e.g., 250K+ tokens) on rare-token handling? | Rare tokens receive few training examples, leading to poorly-trained ('undertrained') embeddings and unstable generation behavior — a trade-off against shorter sequences for common text. |
| 10 | How does increasing context length affect inference cost and latency? | KV cache memory grows linearly with context length; attention compute grows quadratically without optimizations (e.g., FlashAttention, sliding-window attention). Longer context ⇒ higher prefill latency and memory pressure. |
| 11 | Why do many production LLMs (e.g., LLaMA family) train on far more than ~20 tokens/parameter? | To shift compute cost toward one-time training and away from repeated inference — this is 'inference-optimal' rather than Chinchilla 'compute-optimal' training, since inference cost dominates over a model's deployed lifetime. |
| 12 | Quick way to inspect a Hugging Face tokenizer's vocab size and type? | `from transformers import AutoTokenizer; tok = AutoTokenizer.from_pretrained(name); print(tok.vocab_size, type(tok).__name__)`. Exam tip: SentencePiece-based tokenizers expose an `sp_model` attribute distinct from BPE-based ones. |
